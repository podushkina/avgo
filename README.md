# Безопасная сделка — интерактивный тренажёр антискама

Кейс 5 «Антискам тренажёр». Обучающее веб-приложение, которое учит пользователя классифайда
распознавать мошенничество до того, как он совершит рискованное действие.

Продукт состоит из двух связанных частей:

1. **Тренировка по сценариям** — реалистичные ситуации из переписок. Пользователь выбирает
   действие и сразу видит **последствие именно своего выбора**, безопасную альтернативу и разбор
   признаков риска.
2. **Живой диалог с ИИ-мошенником** — языковая модель отыгрывает мошенника, подстраиваясь под роль
   и уровень пользователя. Заранее заготовленного правильного ответа здесь нет, поэтому навык
   приходится применять, а не вспоминать. После разговора выдаётся разбор применённых приёмов и
   допущенных уступок.

## Быстрый запуск

Нужны только Docker и Docker Compose.

```bash
git clone <репозиторий> && cd <репозиторий>
make up-llm          # поднимает всё, включая языковую модель в контейнере
```

Приложение открывается на **http://localhost:8080**.

Первый запуск скачивает модель (~4.7 ГБ), это занимает несколько минут. Прогресс виден в
`docker compose logs -f ollama-pull`. Сервис диалога стартует только после того, как модель
скачана (`depends_on: service_completed_successfully`), поэтому «пустых» ответов в чате не будет.

### Запуск на macOS (быстрый вариант)

Docker Desktop на macOS [не пробрасывает GPU](https://github.com/ollama/ollama/blob/main/docs/faq.mdx),
поэтому модель внутри контейнера считается на CPU и отвечает в разы медленнее. На Маке запускайте
Ollama нативно — она использует Metal:

```bash
brew install ollama && ollama serve &
ollama pull qwen2.5:7b
make up              # ai-service ходит на host.docker.internal:11434
```

### Без языковой модели вообще

Тренировка по сценариям работает независимо от LLM. Чтобы поднять стек без модели, поставьте
в `.env`:

```
LLM_PROVIDER=mock
```

Диалог будет отвечать сценарными заглушками — этого достаточно, чтобы проверить весь
пользовательский путь.

### Полезные команды

```bash
make help       # список команд
make test       # go-тесты обоих сервисов
make lint       # golangci-lint по обоим сервисам
make smoke      # сквозная проверка API поднятого стека
make bench-llm  # сравнить модели-кандидаты на промпте мошенника
make down       # остановить
make clean      # остановить и удалить тома (БД пересоздастся и пересидится)
```

Фронтенд отдельно: `cd frontend && npm ci && npm run dev` (Vite проксирует `/api` на сервисы).

```
   ├─ безопасная альтернатива и её исход
   └─ разбор: почему так + признаки риска
        │

        │

        │        └─ разбор: приёмы собеседника, ваши уступки, что запомнить
        │
        └──► Мой прогресс: история попыток, динамика, что делать дальше
```

### Как устроена система обучения

Тренажёр построен на трёх принципах, вытекающих из бизнес-задачи.

**Учим последствиям, а не правильному ответу.** У каждого варианта есть собственный исход и
вердикт (`safe` / `risky` / `dangerous`). Выбрав опасное действие, пользователь читает не «неверно»,
а конкретно: что произойдёт с его деньгами или аккаунтом. Это то, что переносится в реальную
сделку.

**Промежуточные варианты вместо бинарности.** Кроме безопасного и опасного есть рискованные
действия — формально не катастрофа, но шаг в сторону мошенника («попросить видео товара и внести
предоплату»). За них начисляется частичный балл: 10 / 4 / 0 очков. Так тренажёр отражает реальную
градацию решений и не превращается в набор очевидных вопросов.

**Одно прохождение — не тренировка.** Прогресс показывает динамику между попытками, а диалог с ИИ
каждый раз новый, что даёт повод вернуться.

## Архитектура

```
                            nginx :8080
              ┌─────────────────┼──────────────────┐
        /api/dialog/*        /api/*            /  (React SPA)
              │                 │
        ai-service :8082   api-service :8081
              │                 │
              │            postgres :5432
              ▼
   LLM (OpenAI-совместимый endpoint)
    ├─ macOS      : host.docker.internal:11434 → нативная Ollama (Metal)
    └─ local-llm  : ollama:11434               → Ollama в контейнере
```

nginx выбирает самый длинный совпавший префикс, поэтому `/api/dialog/` уходит в ai-service,
а остальное под `/api/` — в api-service.

| Компонент | Стек |
|---|---|
| Frontend | React 19, TypeScript 6, Vite, Zustand, React Query, Axios |
| api-service | Go 1.26, pgx, goose (миграции в бинарнике через `embed.FS`) |
| ai-service | Go 1.26, свой OpenAI-совместимый клиент, SSE |
| БД | PostgreSQL 18 |
| Модель | qwen2.5:7b через Ollama |

### Почему PostgreSQL

Требование кейса — обосновать выбор.

- **Данные реляционные.** `users → progress → scenarios` — это связи с внешними ключами и
  каскадным удалением. Документная БД потребовала бы поддерживать целостность руками.
- **Нужен и JSON.** Варианты ответа с исходами и разбор ошибок — вложенные структуры переменной
  формы. `jsonb` в Postgres закрывает это без второй базы и без таблицы «ключ-значение».
- **Агрегаты для прогресса.** Динамика результатов — это сортировки и агрегации по времени, то
  есть родная территория SQL.
- **Нагрузка не диктует экзотику.** Профиль — единичные записи и чтения по индексу; ни Redis, ни
  ClickHouse здесь ничего не улучшат, а добавят движущихся частей.
- **Операционная зрелость.** Официальный образ, миграции, знакомство команды — на хакатоне это
  экономит время, которое лучше потратить на продукт.

Сессии диалога намеренно живут **в памяти ai-service**: они короткие, привязаны к одному
разговору и не переживают перезапуск осмысленно. Это убирает лишний слой хранения. Для аналитики
их можно будет складывать в отдельную таблицу.

### Ключевые технические решения

**Правильные ответы никогда не уезжают на клиент.** `GET /api/scenarios` отдаёт только тексты
вариантов. Проверка ответа — отдельный запрос, итоговый счёт считается на сервере по сценариям из
базы. Иначе тест проходится одним взглядом в DevTools.

**Счёт считается по числу вопросов роли, а не по числу присланных ответов.** Иначе попытку можно
накрутить, отправив один верный ответ вместо шести. Неотвеченный вопрос — ошибка.

**Ответ модели стримится через SSE.** На 7B-модели полный ответ приходит за 2–3 секунды, и «немой»
интерфейс всё это время читается как зависший. Со стримингом важна только задержка до первого
токена. В nginx для этого маршрута отключена буферизация.

**Провайдер модели абстрагирован интерфейсом `llm.Client`.** Одна реализация `openaicompat`
покрывает Ollama, OpenAI и любой совместимый прокси — различаются только `LLM_BASE_URL` и
`LLM_MODEL`. Вторая реализация `mock` даёт детерминированные ответы: юнит-тесты не ходят в сеть.

**Ссылки от модели фильтруются.** Модель обязана называть только вымышленные домены на `.example`,
а на выходе стоит санитайзер, который заменяет любой реальный домен на заглушку. Фильтрация
работает и в потоке: токены буферизуются до границы слова, поэтому ссылка не может «просочиться»
по частям.

**Ответ фильтруется и от смены языка.** `qwen2.5:7b` — модель китайского происхождения, и на
длинных диалогах она изредка срывается в китайский посреди предложения. Это воспроизвелось на
живом прогоне. Защита выстроена в три слоя: явный запрет в системном промпте, пониженная
температура (0.7) и вырезание иероглифов тем же потоковым санитайзером, что чистит ссылки.

**Темп обмана задаётся кодом, а не промптом.** 7B-модель не умеет надёжно считать собственные
ходы: на высокой сложности она бесконечно «выстраивала доверие» и за пять реплик не применяла ни
одного приёма — тренироваться было не на чем. Поэтому перед каждой генерацией сервис подставляет
служебную директиву с номером хода: до порогового хода — фаза доверия, начиная с него — конкретный
приём из ротации. Порог зависит от сложности (1 / 2 / 3-й ход).

**Зацикливание обрывается на лету.** Маленькие модели повторяют предложения дословно. Потоковый
санитайзер запоминает уже произнесённые предложения и прекращает выдачу на первом повторе, а
клиенту уходит корректно завершённый текст. Дополнительно выставлены штрафы за повтор
(`frequency_penalty`, `presence_penalty`).

**Лимит токенов — страховка, а не инструмент краткости.** Токены локальной модели ничего не стоят,
но при 26 tok/s длинный ответ превращается в паузу на десяток секунд, а краткость всё равно
задаётся промптом. Поэтому лимит поднят до уровня, который в норме не срабатывает, а если он всё же
сработал — ответ обрезается по границе предложения, чтобы реплика никогда не обрывалась на полуслове.

## API

### api-service

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/api/healthz` | Проверка сервиса и соединения с БД |
| `POST` | `/api/users` | `{external_id}` → пользователь (идемпотентно) |
| `GET` | `/api/scenarios?role=buyer\|seller` | Сценарии роли **без** правильных ответов |
| `POST` | `/api/scenarios/{id}/check` | `{option}` → последствие, вердикт, разбор, признаки риска |
| `POST` | `/api/attempts` | `{user_id, role, answers[]}` → результат и сохранение попытки |
| `GET` | `/api/progress?user_id=` | История попыток пользователя |

### ai-service

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/api/dialog/healthz` | Проверка сервиса |
| `POST` | `/api/dialog/sessions` | `{role, difficulty}` → сессия и первая реплика мошенника |
| `GET` | `/api/dialog/sessions/{id}` | История сообщений |
| `POST` | `/api/dialog/sessions/{id}/messages` | `{text}` → **SSE**-поток ответа |
| `POST` | `/api/dialog/sessions/{id}/finish` | Разбор диалога |

Формат SSE: события `token` (`{"text": "…"}`), `done` (`{"text": "…"}`), `error` (`{"error": "…"}`).

Пример:

```bash
curl -N -X POST localhost:8080/api/dialog/sessions/<id>/messages \
     -H 'Content-Type: application/json' \
     -d '{"text":"Здравствуйте! Да, товар в наличии."}'
```

## Выбор модели

Модель выбиралась замерами на MacBook (Apple Silicon, 16 ГБ), скрипт — `make bench-llm`.

| Модель | Скорость | Вывод |
|---|---|---|
| `qwen2.5:3b` | 59 tok/s | Быстрая, но русский бессвязный уже на второй реплике |
| `deepseek-r1:8b` | 24 tok/s | Reasoning-модель: `content` пустой, весь вывод уходит в `thinking` |
| `gemma-4-abliterated:12b` | 17 с на ответ | Тоже reasoning, для чата непригодна |
| **`qwen2.5:7b`** | **26 tok/s** | Связный русский, держит роль, не reasoning — **выбрана** |

Главный вывод: reasoning-модели для этой задачи не подходят в принципе — они возвращают пустой
`content`. Клиент считает такой ответ ошибкой и говорит об этом явно.

## Тесты и линтеры

```bash
make test                      # 56 go-тестов
cd frontend && npm test        # 9 тестов (Vitest + Testing Library)
make lint                      # golangci-lint, 0 замечаний
cd frontend && npm run lint    # ESLint, 0 замечаний
```

Покрыты самые важные участки:

- **подсчёт очков** — накрутка неотвеченными вопросами, чужие сценарии, вариант вне диапазона,
  частичный балл за рискованное действие, сбор пропущенных признаков риска;
- **клиент модели** — сборка токенов, остановка на `[DONE]`, ошибки HTTP и потока, распознавание
  пустого ответа reasoning-модели;
- **санитайзер ответа модели** — подмена реальных доменов и вырезание иероглифов, в том числе
  разорванных между токенами;
- **сессии** — TTL, продление активностью, лимит реплик, изоляция истории;
- **анализ диалога** — распознавание приёмов и уступок, отсутствие дублей;
- **фронтенд** — разбор SSE-потока (включая кадры, разорванные между чанками), показ последствия
  выбора, блокировка повторного ответа, отправка попытки.

Конфигурация линтеров: `.golangci.yaml` в корне, `frontend/eslint.config.js`,
`frontend/.prettierrc.json`.

TypeScript зафиксирован на ветке 6.x намеренно: `typescript-eslint` пока не поддерживает
TypeScript 7, а рабочий ESLint для этого проекта важнее самой свежей версии компилятора.
Остальные зависимости — последние на момент сдачи.

## Ограничения MVP

- **Аутентификации нет.** Пользователь опознаётся по идентификатору из `localStorage`. Для MVP
  этого достаточно: тренажёр не хранит ничего чувствительного. В продакшене — учётная запись
  платформы.
- **Сценариев по 6 на роль.** Модель данных рассчитана на расширение: контент лежит в миграции
  `00002_seed_scenarios.sql` и добавляется без изменения кода.
- **Сессии диалога не переживают перезапуск ai-service** и не масштабируются на несколько
  реплик — они в памяти процесса. Лечится вынесением в Redis.
- **Анализ диалога построен на правилах,** а не на LLM: это быстро, детерминированно и
  тестируемо, но нестандартные формулировки уступок он может пропустить.
- **Адаптивная сложность влияет только на промпт** ИИ-мошенника, а не на набор сценариев теста.
- **Модель может отвечать медленно** на слабом железе; при CPU-инференсе ответ занимает
  десятки секунд. Для демонстрации предусмотрен `LLM_PROVIDER=mock`.
- **Прогресс не синхронизируется между устройствами** — идентификатор локальный.

## Использование ИИ

**В самом продукте.** Языковая модель играет мошенника в режиме живого диалога — это ключевая
механика, а не украшение: она даёт неограниченное число неповторяющихся тренировок и заставляет
применять навык, а не вспоминать заученный вариант. Модель локальная (Ollama), внешние API не
используются, ключи не нужны.

**В разработке.** Ассистент (Claude) применялся на следующих этапах:

- анализ ТЗ кейса и проектирование архитектуры, включая выбор схемы «2 сервиса + gateway»;
- генерация и редактура контента сценариев мошенничества с последующей ручной вычиткой;
- написание шаблонного кода: CRUD-хендлеры, конфигурация Docker, миграции, каркас тестов;
- подбор и замеры модели: скрипт `scripts/bench_llm.py` и сравнение кандидатов.

Все архитектурные решения, содержание сценариев и итоговый код проверены командой.
